- **Verified with real runs, not just a successful build.** Simulated a clean checkout by moving aside local `data/index/`, `data/generated/`, and `data/database/app_state.db` before `docker compose up --build`. Confirmed: (1) `docker compose ps` reports both services `healthy`; (2) `GET /health` returns instantly with `last_indexed: null` on the first run — no model call; (3) a real `POST /ask` question through the containerized FastAPI service returned a correct hybrid-retrieval agent answer with real citations, proving the pre-baked embedding model, `company.db` fixture, and live GitHub connector all work inside the container without any extra setup; (4) after `docker compose down && up`, `GET /health`'s `last_indexed` showed the prior run's timestamp — the bind mount persisted the semantic index and `app_state.db` across a full container recreation; (5) a direct call to `load_github_issues_connected` against a nonexistent repository, run inside the running `api` container, returned the same graceful fallback-with-disclosure behavior verified in Phase 4 — unchanged by containerization.
- **Host-container UID alignment confirmed, not assumed.** The container's non-root user is fixed at uid/gid 1000; the actual host user (`alex`) is also uid/gid 1000, confirmed via `id -u`/`id -g` before choosing this — the bind-mounted `data/` files came out owned by `alex:alex` with no permission errors. `README.md` documents a `chmod -R a+rwX` fallback for a host where this doesn't hold, rather than adding entrypoint-script complexity to solve it generically.
- **Local dev state restored after testing** — the moved-aside `data/index/`, `data/generated/`, and `data/database/app_state.db` (this session's real Phase 8 evidence) were copied back once containerized verification finished; confirmed via `git status` that only the intended new/modified files (`Dockerfile`, `docker-compose.yml`, `.dockerignore`, `README.md`, `deliverables/DECISIONS.md`) are tracked changes.
- **Deliberately not built:** a `docker-entrypoint.sh` that `chown`s the data directory and drops privileges (the fixed-uid approach was sufficient on this host and keeps the image simpler, per the phase's "keep the packaging modest" instruction); a CI job that runs the container build/health checks automatically; pinning the `ghcr.io/astral-sh/uv` base image to a specific version tag (used `:latest`, matching `uv`'s own Docker documentation pattern, accepted since dependency versions are already locked by `uv.lock` regardless of which `uv` binary installs them).
- **Not exercised this phase:** running the container against a genuinely offline host (no network at all) — the fallback was verified via a real 404 against a nonexistent repository (network reachable, GitHub responded, then the code chose to fall back), not via a fully air-gapped test. Recorded as a minor gap, not a contradiction of the "reassurance" decision, since the fallback code path itself is identical either way and was already exercised on a real network failure in Phase 4.
- **A real finding disclosed, not fixed:** the built image is ~9.6 GB (`docker images` after the real build above), almost entirely `torch`'s GPU-enabled wheels pulled in transitively by `sentence-transformers` — this container never uses a GPU. A CPU-only `torch` wheel (`uv`'s `[tool.uv.sources]`/`--extra-index-url` pointed at PyTorch's CPU index) would likely cut this dramatically, but that's a dependency-resolution change to `pyproject.toml`/`uv.lock` outside this phase's "package what already exists" scope — flagged as a Phase 9/10 residual risk rather than patched under this phase's own instructions.
