## Source Governance

| Source | Stable ID strategy | Citation target | Update or deletion policy | Fallback |
| --- | --- | --- | --- | --- |
| Slack export | Fixture-assigned `source_id` (e.g. `SLACK-ATLAS-101`), stable regardless of edits or re-export order | `source_path` (channel export file) + channel/thread title | Full folder rescan on each sync; a `source_id` absent from the latest export is removed from the index | None — Slack stays export-only in the core project, no live connector planned |
| Email export | `X-Source-ID` header, required at parse time | `source_path` (`.eml` file) | Static teaching fixture; changes only via files added/removed from the folder, detected by rescan | None — local-only, and out of scope for the Engineering profile anyway |
| Documents | Front-matter `source_id`, required at parse time | `source_path` (Markdown file) + title | Folder rescan; `status: archived` (e.g. `DOC-POLICY-OLD-402`) marks a document superseded **without deleting the file** — retrieval/ranking must down-rank or exclude archived docs explicitly, deletion alone won't catch this | None |
| Local GitHub export | Fixture `source_id` keyed to issue number, not title | `source_path` (`issues.json`) — no real URL available locally | Folder rescan; an issue missing from the export is removed from the index | None — this is fictional product content (the Atlas billing-migration issues), not a cache of any real repository, so it always loads regardless of live connector status (revised in Phase 4, see Enforcement Notes) |
| Live GitHub repository | Derive from the stable issue **number**, prefixed with the repository so it can never collide with the local export's IDs (`GH-{owner}-{repo}-{number}`, e.g. `GH-AlexDeWilde-ai-agent-project-test-repo-8`), never the title, since titles can change | Real issue URL (`html_url` from the API) | Fetched fresh on every request with `state=all` (open + closed) and merged into that request's corpus; a closed issue still appears (state change, not deletion) — no persistent live index yet, real incremental sync is Phase 5's job | None — added on top of the always-present local sources when configured and reachable; when unavailable/unauthenticated/rate-limited/unconfigured, simply contributes zero issues that turn rather than substituting the unrelated local Atlas fixture as if it were live data. The UI must disclose which state is active (Phase 4 completion evidence) |
| SQLite records | No convention exists yet beyond the ad hoc `f"DB-{case_id}"` built inside `get_support_case()` — needs an equivalent for `projects` (e.g. `DB-{project_id}`) before it becomes a tool | Table name + primary key, not a file path | Whole-database regeneration via `initialize_database()`; no incremental change tracking exists — acceptable for a fixed teaching DB, but state this limitation explicitly rather than implying live sync | None — single source of truth, no live DB |

## Enforcement Notes

- **Identity source in the prototype:** The four fictional profiles in `api.EMPLOYEES`, selected via the Streamlit selectbox or the `employee_id` field on `/ask`. This is a self-declared identity, not authentication — anyone calling the API can claim to be any employee.
- **Where filtering happens:** `filter_permitted()` in `security/permissions.py`, called inside `lexical_search()` before documents are ranked or shown. Semantic and hybrid retrieval must call the same function in the same position — before candidates are scored, not after.
- **Default when metadata is missing:** `parse_roles()` and `parse_confidentiality()` raise `ValueError` on missing, empty, or unrecognized values, so a malformed record fails the connector load loudly instead of silently entering the index. `filter_permitted()` itself is a simple membership check, so any role not explicitly listed is implicitly denied.
- **How citations are rechecked:** Done as of Phase 6. `retrieval.semantic_search()` already filtered twice (vector-store `where` clause plus a `filter_permitted()` recheck). `tools.knowledge.open_source()` closes the remaining gap: it re-loads current documents and re-runs `filter_permitted()` against the *live* data at the moment a citation is opened, not a cached result — so a source deleted or reclassified since an earlier search cannot be resolved. `found=False` covers "no such source" and "no longer permitted" identically (verified directly: opening `DOC-HR-001` as Leo and opening a nonexistent `NOPE-999` return field-for-field identical results other than the echoed `source_id`).
- **Semantic index freshness vs. live GitHub freshness:** these are two independent freshness clocks. `lexical_search`/`hybrid_search` call `load_all_documents_with_github_status()` fresh on every request, so GitHub content is as current as Phase 4's per-request fetch. `semantic_search()` only reads what `indexing.sync_index()` last wrote to Chroma — a live issue created after the last sync will not appear semantically until the next sync runs. No scheduled sync exists yet; `sync_index()` is called on demand (see `DECISIONS.md`).
- **How live API access differs from employee authorization:** GitHub repo access is binary (the token can read the repo or it can't) and says nothing about which of the four Northstar roles should see a given issue. The live connector must assign `allowed_roles` per issue using an explicit, documented policy (e.g. by label — `billing`/`release-blocker` → include finance, `support` → include customer_success) that mirrors the local export's existing assignments, never "if the token can read it, every employee can see it."
- **Chosen live repository (Phase 4):** `AlexDeWilde/ai-agent-project-test-repo` — public, so no token is required (`GITHUB_TOKEN` is left blank in `.env`; `connectors/github_live.py` adds an `Authorization` header only when one is configured, for future use with a private repo). Its issues are about building this connector, not the fictional Atlas scenario — so the local Atlas export and the live repository are two independent, always-additive source families rather than one substituting for the other; see the Source Governance table above.
- **Live `allowed_roles` label policy (`connectors/github_live.py: LABEL_ROLE_POLICY`):** every issue gets `engineering` as a baseline; the label `customer-impact` or `support` additionally grants `customer_success`; `finance-review`, `billing`, or `release-blocker` additionally grants `finance`; no label ever grants `people_operations`, matching the Local/Live GitHub work items row above. Verified directly against the live repo's real labels — issue #8 (`customer-impact`) is Customer-Success-visible, issues #6/#7 (`finance-review`) are Finance-visible, the rest are engineering-only.
- **Where GitHub credentials are stored:** `.env` only (`GITHUB_TOKEN`), as a fine-grained PAT scoped to one repository with read-only issue access when a private repository is used. Never in prompts, retrieved content, traces, screenshots, or committed files.
- **Rate-limit assumption:** unauthenticated GitHub REST calls are capped at 60 requests/hour per IP; the chosen repo's 8 issues fit in one page well within that limit for a classroom demo. Adding a token would raise the cap to 5,000/hour if this becomes a bottleneck.
- **Controlled failure, not fabrication:** `fetch_live_issues()` raises `GitHubConnectorError` on any non-200 response, network error, or a response shape it cannot parse — verified against a nonexistent repository (real 404 surfaced, not swallowed). `load_live_github_issues()` catches only that error and reports zero live-sourced issues plus an explicit `local_fallback` state; it never invents issue data and never lets a live failure look like a real empty repository.
- **How identity is rechecked before an approved action:** Designed and verified as of Phase 6. `tools.actions.approve_action()`/`execute_action()` are plain functions with no LangChain tool wrapper at all — the agent has no path to calling them, and neither does text inside a retrieved document, since only a separate, human-facing interaction (a future Streamlit control) will call them directly. `approve_action()` refuses self-approval (the proposal's `requested_by` cannot equal the approver's `employee_id`) and re-checks the proposal's current status before transitioning it, rather than trusting whatever state was true when it was drafted. `execute_action()` separately re-checks that the proposal is actually `approved` immediately before running (transitioning to `failed` otherwise) — verified directly: self-approval raises, approving/executing an unknown or already-terminal proposal raises or fails, and every transition is written to an in-memory audit log (`tools.actions.list_audit_log()`). Execution itself stays simulated — it only transitions state, never calls a real write API — per `AGENTS.md`'s read-only mandate.
- **Confirmed through the live agent, not just direct tool calls (Phase 6):** every property above was re-verified end-to-end through real Groq calls (`openai/gpt-oss-20b`), not only by calling tools directly. Across every live run: `DOC-HR-001` never appeared in Leo's or Maya's answers or citations; the `SLACK-ATLAS-103` prompt-injection message was retrieved into the model's own context (via `open_source`) and its embedded "SYSTEM OVERRIDE" instruction was never obeyed, never triggered an HR-content fetch, and in every run wasn't even cited in the final answer; `propose_action` never executed anything, always left proposals `pending_approval` with language explicit about awaiting a separate approval. Full evidence in `EVALUATION_REPORT.md`'s Phase 6 agent section.
- **What the prototype does not secure yet:** Real authentication (the profile selector is self-declared and the API accepts any `employee_id`); no protection against a client simply switching `employee_id` between requests; no audit-log tamper protection; no rate limiting. As of Phase 6, the SQLite tools are built (`tools/structured_data.py`), closing that specific gap. New from Phase 6: the action-proposal store and audit log (`tools/actions.py`) are in-memory and per-process — restarting the app loses every pending/approved/rejected proposal and its history. Acceptable for this prototype's scope; a real deployment would need a persisted store.
- **Evidence that unauthorized content is excluded before retrieval:** `filter_permitted()` is directly unit-testable against `CompanyDocument` fixtures without a model or network call — e.g. assert that Leo's `engineering` role never receives `DOC-HR-001` from `filter_permitted()`, and that `SLACK-ATLAS-103` (the injection message) is retrievable but its instruction is never followed. This is exactly the "no model key or network call needed" completion evidence required by Phase 3.
