### Decision: Split the SQLite access policy by table instead of by database

- **Phase:** 2 — Access matrix
- **Context:** The template's matrix treats "Financial records" as one row, but the database has three tables of different sensitivity: `customers`/`support_cases` (revenue, account value, case ownership) and `projects` (release status/target date). Leo's Engineering profile needs the Atlas project status (`projects` table) for its priority questions but has no business need for customer or revenue data.
- **Options considered:** (1) Deny Engineering all database access, forcing release-status questions through GitHub/Slack/docs only; (2) Allow Engineering the whole database; (3) split the matrix row so Engineering gets `projects` only, denied on `customers`/`support_cases`.
- **Coding-agent contribution:** Inspected `database.py` and confirmed no role or confidentiality metadata exists at the schema or `get_support_case()` level today — the split is a policy decision that has no enforcement yet.
- **Evidence reviewed:** `src/company_assistant/database.py` (schema and the one existing lookup function); `deliverables/PRODUCT_BRIEF.md`'s in-scope/out-of-scope boundaries.
- **Decision and owner:** Option 3, split by table — confirmed by the AI PM.
- **Consequences or follow-up:** Implemented immediately in `database.py` (ahead of Phase 6) rather than deferred, since the check is small, contained to the data layer, and removes a live gap from the risk register before any tool can call it. `get_support_case()` now takes an `employee` parameter and denies non-`customer_success`/`finance` roles by returning `None` (same shape as "not found," so a denied role can't infer existence); a new `list_project_status()` follows the same pattern for `customer_success`/`engineering`/`finance`, returning `[]` when denied. Verified directly with normal, denied, and not-found inputs (no model or network call). Phase 6 still needs to wrap both functions as typed LangChain tools that supply `employee` from the caller's verified identity, not from model input.
- **Status:** Accepted

### Decision: Record the live GitHub repository as committed project config, not a per-developer `.env` value

- **Phase:** 4 — Live GitHub connector (prep)
- **Context:** Chose `AlexDeWilde/ai-agent-project-test-repo` (new, public, created for this project) as the one live GitHub source required by file `04`. `04` only requires the **token** to live in `.env` ("Keep the token in `.env`"); it says nothing about the repository name needing the same treatment. The repository identifier is not sensitive — it's a public URL — so requiring every group member to privately discover it and hand-copy it into their own untracked `.env` is pure friction with no security upside.
- **Options considered:** (1) Leave `GITHUB_REPOSITORY` as a blank line in `.env.example`, same as the token, relying on each collaborator being told the value out-of-band; (2) fill in the real value directly inside `.env.example`; (3) record it in this decision log and `ACCESS_MATRIX.md` (both committed, both places a collaborator would already look for source configuration), and have Phase 4's connector code fall back to this value as a committed default when the `GITHUB_REPOSITORY` env var is unset.
- **Coding-agent contribution:** Confirmed no config-loading code exists yet (Phase 4 not implemented) and that `python-dotenv` is a declared but unused dependency, so there's no existing convention this decision needs to conform to.
- **Evidence reviewed:** `04-connected-rag-and-agent.md` (exact wording of the `.env` requirement — token only), `.env.example`, `pyproject.toml`.
- **Decision and owner:** Option 3 — confirmed by the user.
- **Consequences or follow-up:** `.env.example` keeps `GITHUB_REPOSITORY=` blank (avoids implying it's secret alongside the token) but now points readers here. `ACCESS_MATRIX.md`'s "Live GitHub work items" row and Source Governance table, previously abstract ("the live repo"), now name the actual repository. When Phase 4's connector is implemented, it must treat `os.environ.get("GITHUB_REPOSITORY")` as an override of this documented default, not a requirement — so the app runs against the shared repo with zero local setup, while still letting a developer point at a different repo temporarily via their own `.env`. If the override path is ever used, that fact should be visible in the trace/UI (same "disclose which state is active" requirement already flagged for live-vs-fallback in `PROGRESS_LOG.md`), so a silently overridden repo doesn't look identical to the team default.
- **Status:** Accepted

### Decision: Phase 8 comparative evaluation — scope, thresholds, and dashboard design

- **Phase:** 8 — Run a comparative evaluation
- **Context:** File `05` requires comparing lexical/semantic/hybrid (at minimum) on a shared question set, adding cases for the selected workflow, the live GitHub source, index updates, feedback, and human approval, recording results by layer, defining pass/fail thresholds *before* reading final results, and building a compact, inspectable Streamlit view.
- **Options considered and decisions (all confirmed by the AI PM before implementation):**
  1. **New eval cases vs. narrative evidence.** Rather than formalizing every required scenario as a fixed case, added exactly 2 to `data/evaluation/cases.json` — `EVAL-013` (live-source_evidence) and `EVAL-014` (feedback_capture) — since the workflow (EVAL-001-003), index lifecycle (EVAL-011), and human approval (EVAL-010) were already covered. The 4 approval outcomes (approve/edit/reject/fail) stayed narrative evidence, matching Phase 6's existing pattern, rather than reformalized into more cases.
  2. **Thresholds locked in `runner.py::THRESHOLDS` before any run**, quoted (not restated) by `EVALUATION_REPORT.md` so the two can't drift: forbidden-evidence-exposed and unapproved-actions-executed at 0 as hard release blockers (per file `05`'s own explicit rule); unsupported-factual-claims added as a third blocker at 0, beyond file `05`'s literal two, on the AI PM's judgment that citation integrity is equally load-bearing for this product's trust model; recall/latency/abstention/tool-selection targets set as informational, not blocking.
  3. **Compare 4 variants, not the required 3** — lexical, semantic, hybrid, and the agent as an explicit 4th column, since the agent is what actually ships and every deterministic-mode gap it closes (abstention, tool use, memory, approval) is exactly the evidence a release decision needs.
  4. **Dashboard as its own Streamlit page** (`pages/Evaluation.py`, native multipage nav) rather than a tab inside `app.py`, so chat session state and evaluation state never collide.
  5. **A reusable runner** (`src/company_assistant/evaluation/runner.py`), independent of Streamlit per `AGENTS.md`, with a live "Run evaluation now" button on the dashboard streaming per-case progress via `st.status` — chosen specifically so the human team could watch a real run happen in the browser rather than only reviewing a static table afterward.
  6. **Accept Groq rate-limit risk rather than build retry/backoff first** — any failure during the run is itself evidence for the risk register, not a reason to delay Phase 8.
  7. **Clear `data/database/app_state.db` before running** (gitignored, regenerates its schema automatically) so Phase 8's feedback/proposal counts reflect this phase's real runs, not leftover Phase 6/7 test data.
- **Coding-agent contribution:** Read `AGENTS.md`, files `01`-`05`, `PROGRESS_LOG.md`, `DECISIONS.md`, the current `EVALUATION_REPORT.md`, and `app.py` before proposing options; built the runner and dashboard; ran the evaluation live at the human team's request so it was watched directly rather than reported after the fact.
- **Evidence reviewed:** `05-evaluation-and-release.md`'s exact Phase 8 requirements; the existing `cases.json`/`cases.py`/`service.py`/`agent.py`/`app_state.py`/`api.py` contracts; `PROGRESS_LOG.md`'s Phase 7 open items (the residual risks this phase's real run was expected to re-check).
- **Decision and owner:** All seven choices approved by the AI PM before implementation began.
- **Consequences or follow-up:** Running the real evaluation surfaced two things worth recording as their own small decisions, not silently absorbed into the numbers:
  - **A scoring bug, not a product bug.** The runner's first pass graded `EVAL-006` (indirect prompt injection) on whether the agent cited the injection-carrying message — the wrong test; the real pass condition is forbidden-evidence absence, which held throughout. Fixed the scoring rule and **rescored the already-collected real results from their raw fields** (`rescore_results()`) rather than re-running the matrix, since the underlying observed model behavior hadn't changed, only a wrong grading rule had.
  - **A real GitHub rate-limit event, handled by adding a token, not by engineering around it.** The unauthenticated GitHub API's 60-requests/hour cap was exhausted during testing; `EVAL-013` correctly fell back to the local export and correctly abstained rather than fabricate live data — itself valid evidence of correct degradation. The AI PM chose to add a fine-grained, Issues-read-only `GITHUB_TOKEN` (local `.env`, gitignored, never committed) over accepting the degraded result, specifically to get one genuine clean live-citation data point; `rerun_case()` re-ran only `EVAL-013` afterward rather than the full matrix, to avoid spending Groq quota on cases whose results didn't need to change.
  - The real run also surfaced one finding neither fix nor scope decision addresses: **agent-path latency (19.2s median, up to 65.5s) badly misses the 8s target set before the run.** Left as an open, disclosed residual risk for Phase 9/10 rather than patched under time pressure inside Phase 8's own scope.
- **Status:** Accepted

### Decision: Phase 7 product experience — seven scope decisions plus implementation-level resolutions

- **Phase:** 7 — Complete the product experience
- **Context:** Phases 1-6 built a complete application service (deterministic modes, the Groq-backed agent with 6 tools, persisted proposals/conversation history) that neither `app.py` nor `api.py` reached — both still called `answer_with_baseline` only. File `04`'s Phase 7 spec requires connecting the finished agent/approval stack to both interfaces with visible trust boundaries (identity/role, retrieval mode, citations, contradiction/staleness warnings, tool trace, last-indexed status, a separate approval control, useful/not-useful feedback).
- **Options considered and decisions (all confirmed by the AI PM before implementation):**
  1. **Chat always runs the agent** (not a lexical/semantic/hybrid/agent selector). The three deterministic modes stay in `service.py`, untouched, reserved for Phase 8's comparison only.
  2. **One `conversation_id` (UUID) per Streamlit session**, generated client-side and reused across turns; FastAPI's `AskRequest.conversation_id` stays optional, with the server generating one when omitted.
  3. **Feedback uses fixed reason categories** (`missing_source`, `wrong_answer`, `stale_evidence`, `bad_citation`, `other`), not free text — easier for a future dashboard to aggregate.
  4. **Pending approvals surface as a persisted, always-visible panel** (queried from `app_state.py` by employee, not held in session state), so a proposal survives a page reload.
  5. **FastAPI gets full endpoint parity now**: `GET /proposals`, `POST /proposals/{id}/decide`, `POST /feedback`, plus `/ask` wrapping its response as `{conversation_id, answer}` and `/health` gaining `last_indexed`.
  6. **`Answer` gains a structured `warnings: list[str]` field**, populated from `compare_sources` results, firing regardless of whether the model's own answer text mentions the stale source (errs toward disclosure).
  7. **Last-indexed status is read from the on-disk manifest directly** (`read_last_indexed`, no `SemanticIndex` construction, so `/health` keeps its "no model call" contract) and shown unconditionally in the Streamlit sidebar.
  - Six follow-on implementation questions, also confirmed (recommended option chosen in each case): `/ask` wraps its response rather than using a header; proposal double-submission is a documented residual risk, not UI-locked; `Answer.answer_id` uses a pydantic `default_factory` (zero changes needed in `service.py`); the archived-source warning fires regardless of answer-text grounding; a cold-start "Never" last-indexed status is acceptable (no eager-build button); an employee switch mid-session resets `conversation_id` and chat history in `app.py` only (not a deeper fix to `app_state.get_conversation_history`).
- **Coding-agent contribution:** Read the full application service layer before proposing options; a Plan sub-agent then designed the concrete wiring (exact model fields, SQL schema, FastAPI routes, Streamlit widget layout) and surfaced the six follow-on questions above rather than silently picking an answer to any of them.
- **Evidence reviewed:** `04-connected-rag-and-agent.md`'s Phase 7 spec (exact required trust-boundary elements), the current `app.py`/`api.py`/`agent.py`/`app_state.py`/`indexing.py`/`models.py`, and `PROGRESS_LOG.md`'s Phase 6 open items (EVAL-001/003 unresolved through a live agent call).
- **Decision and owner:** All thirteen choices approved by the AI PM before implementation began.
- **Consequences or follow-up:** Implementing decision 6 surfaced a real, unplanned finding: the model often answers EVAL-001/003-style questions correctly *without* calling `compare_sources` (the archived source's own wording already flags it), leaving `warnings` empty despite a correct answer. Fixed with one added system-prompt sentence (not part of the original seven decisions, but a small, in-scope refinement needed to make decision 6 actually work) — verified reproducible across repeated runs. A second finding, `compare_sources`'s `status` field only exists on the `documents` connector (not email/Slack), was **not** silently patched with a date-recency heuristic — recorded as a residual risk in `EVALUATION_REPORT.md` for a separate Phase 8 decision instead of expanding this phase's scope unilaterally. All verification for this phase used direct function calls, a real running FastAPI server, and Streamlit's official headless `streamlit.testing.v1.AppTest` API (no browser-automation tool was available in this environment) — real widget interactions (selectbox, chat input, `st.feedback`, sidebar form submits) were programmatically driven and their effects on persisted state and rendered output inspected, not just asserted from reading the code.
- **Status:** Accepted

### Decision: Phase 9 container packaging — topology, build, embedding cache, data persistence, secrets, health checks, and network egress

- **Phase:** 9 — Package the product
- **Context:** File `05`'s Phase 9 requires containerizing the completed product (Streamlit + FastAPI + required local data + documented env vars) so a teammate can start it from a clean checkout without repairing paths or copying hidden files, while keeping secrets outside the image, preserving the local GitHub fallback, making persistent index/feedback locations explicit, and exposing a model-free health endpoint. `app.py` and `src/company_assistant/api.py` are independent entry points into the same package (Streamlit never calls the API over HTTP), so "containerize the product" required several judgment calls with no single obvious default.
- **Options considered and decisions (all confirmed by the AI PM before implementation):**
  1. **Topology.** (a) One container running both processes via an entrypoint script; (b) docker-compose with two services built from one shared image. Chose (b) — one process per container matches Docker convention and keeps each service's health check and restart behavior independent, at the modest cost of a second compose service definition.
  2. **Build tooling.** `uv`-based multi-stage `Dockerfile` (`uv sync --locked` against the committed `uv.lock`), not plain `pip install`, per `AGENTS.md`'s "locked `uv` environment" rule. Dependency installation is layered separately from the source `COPY` so dependency-only changes don't invalidate the build cache.
  3. **Embedding model.** `sentence-transformers/all-MiniLM-L6-v2` (loaded by `indexing.py`'s `HuggingFaceEmbeddings`) is pre-downloaded into `/opt/hf-cache` during the image build, rather than left to download on first semantic/hybrid request. The runtime stage also sets `HF_HUB_OFFLINE=1`/`TRANSFORMERS_OFFLINE=1` so the cached model is never re-validated over the network even though egress is otherwise left on (decision 7) — makes the comparative-evaluation demo (Phase 8) reliable and fast regardless of network conditions in the room.
  4. **Data: baked in vs. persisted.** `data/raw/` and `data/database/company.db` (the committed, reproducible fixture) are copied into the image so it is self-contained. `data/index/` (Chroma store), `data/database/app_state.db` (proposals/feedback/conversation history), and `data/generated/` (evaluation results) are excluded from the image (`.dockerignore`) and instead persist through a single `./data` bind mount shared by both compose services — the same on-disk layout the team already uses locally, so nothing new to learn, and `docker compose down`/`up` doesn't lose approvals or feedback.
  5. **Secrets.** `GROQ_API_KEY`, `GITHUB_TOKEN`, `GITHUB_REPOSITORY` reach the containers only via compose's `env_file: .env`; `.env` is excluded from the build context (`.dockerignore`), so it can never end up baked into an image layer.
  6. **Health checks.** Both compose services get a `healthcheck` reusing existing, model-free endpoints — `GET /health` (FastAPI, already reads only the on-disk manifest) and Streamlit's built-in `/_stcore/health` — implemented as a Python `urllib` one-liner rather than adding `curl` to the slim base image. No new application code.
  7. **Network egress.** Left on by default (no image/network changes). The live GitHub connector's existing fallback-on-failure logic (Phase 4) is unchanged and was re-verified inside the container, so an unset `GITHUB_TOKEN` or blocked network degrades to the local fixture exactly as it does outside Docker — recorded here as a documented reassurance for whoever runs the container next, not a new capability.
- **Coding-agent contribution:** Read `05-evaluation-and-release.md`'s Phase 9 spec, `app.py`/`api.py`/`indexing.py` to confirm the two entry points and the embedding-model load path, `pyproject.toml`/`.gitignore`/`data/` layout to determine what's already a committed fixture versus gitignored runtime output, and grepped the codebase to confirm no runtime code reads `deliverables/`/`README.md`/the numbered course files before excluding them from the build context. Presented all seven options to the AI PM before writing any Docker files.
- **Evidence reviewed:** `05-evaluation-and-release.md` (exact Phase 9 requirements and completion evidence bar); `src/company_assistant/indexing.py` (embedding model name and load site); `.gitignore` and `git ls-files data/` (fixture vs. generated data boundary); `README.md`'s existing local run commands (`uv run streamlit run app.py`, `uv run uvicorn company_assistant.api:app`); the host environment's own uid/gid (1000), used to size the container's non-root user against the `./data` bind mount.
- **Decision and owner:** All seven choices approved by the AI PM before implementation began.
- **Consequences or follow-up:** The container's non-root user is fixed at uid/gid 1000 to match this host's default first-user id and avoid bind-mount write failures; documented in `README.md`'s new Docker section as a `chmod -R a+rwX data/index data/generated data/database` fallback for a host where that assumption doesn't hold — not solved generically (e.g., a runtime entrypoint that `chown`s and drops privileges), since that adds complexity the phase's "keep packaging modest" instruction doesn't ask for. Two containers now read/write the same SQLite files (`app_state.db`, the Chroma `manifest.json`/sqlite store) concurrently through one bind mount — acceptable because this already happens locally today (Streamlit and `uvicorn --reload` run as two independent host processes against the same `data/` directory), so containerizing introduces no new concurrency exposure. Authentication, secret rotation, backups, monitoring, provider contracts, and source-level authorization remain explicitly out of scope, per the phase's own instruction not to claim production readiness from containerization alone.
- **Status:** Accepted
